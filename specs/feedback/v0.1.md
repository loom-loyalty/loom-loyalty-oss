# Feedback for APIs: users and agents (v0.1, draft)

Status: draft, version 0.1. Published by Loom Loyalty under the Apache License 2.0. Loom Loyalty's API is the reference implementation. Expect changes in 0.2 once real feedback comes in.

## Why

Agents now call APIs as often as people do. When an agent can't work out how to use an API, the provider usually never finds out: the agent gives up, retries, or guesses. People hit the same walls in docs and screens.

This spec defines one small resource that any API can offer. Users and agents use it to say where the API, its docs, or its agent instructions let them down, and then to check what happened.

## Discovery

A provider that implements this spec:

1. Exposes an operation with `operationId: createFeedback` in its OpenAPI document.
2. Adds a line to its `llms.txt`: `Feedback: <absolute URL of the feedback collection>`.
3. Describes the resource in any MCP server it runs, using tools named `create_feedback`, `get_feedback` and `list_feedback`.

## Resource

| Method and path      | What it does                                                                                   |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `POST /feedback`     | Send feedback. Returns `200` or `201` with the stored item. A new item has `status: RECEIVED`. |
| `GET /feedback/{id}` | Read one item the caller sent. An item the caller didn't send returns `404`.                   |
| `GET /feedback`      | List the caller's own items, newest first, using the provider's usual pagination.              |

Use the same authentication as the rest of the API. A provider may also accept feedback without authentication; this version doesn't define how.

Responses use the provider's usual envelope and pagination. Loom Loyalty, for example, wraps every body in `{ "success", "data" }`, and a create adds `eventId` and `eventDateTime`. The item itself is the same everywhere.

### Request body

| Field           | Required | Notes                                                                                               |
| --------------- | -------- | --------------------------------------------------------------------------------------------------- |
| `submitterType` | no       | `USER` or `AGENT`. Self-reported. A provider may override it when it knows the caller is a machine. |
| `subject`       | yes      | `{ "type": ..., "ref": ... }`: what the feedback is about. Types are listed below.                  |
| `kind`          | yes      | What went wrong. Kinds are listed below.                                                            |
| `rating`        | no       | `POSITIVE` or `NEGATIVE`, for a thumbs up or down.                                                  |
| `goal`          | no       | What the submitter was trying to do. Up to 500 characters.                                          |
| `expected`      | no       | What they expected. Up to 2,000 characters.                                                         |
| `actual`        | no       | What happened instead. Up to 2,000 characters.                                                      |
| `suggestion`    | no       | What would have helped. Up to 2,000 characters.                                                     |
| `requestIds`    | no       | Up to 10 request ids from the provider's responses, so it can find its own logs.                    |
| `httpStatus`    | no       | The status code the submitter got.                                                                  |
| `agent`         | no       | `{ "name", "version", "model", "sdk" }`, all optional strings, self-reported.                       |
| `docsUrl`       | no       | The docs page that misled the submitter.                                                            |

Send an `Idempotency-Key` header of up to 200 letters, digits, `.`, `_`, `:` or `-`. A key belongs to the submitter who sent it: the same submitter sending the same key again gets the item it created the first time, as it is now (its current `status`), instead of a second copy. A provider never matches one submitter's key against another submitter's items.

### Subject types

| `subject.type`       | `subject.ref`                                  |
| -------------------- | ---------------------------------------------- |
| `API_OPERATION`      | The OpenAPI `operationId`                      |
| `MCP_TOOL`           | The MCP tool name                              |
| `AGENT_INSTRUCTIONS` | `llms.txt`, or a skill or prompt identifier    |
| `DOCS_PAGE`          | The page URL                                   |
| `PRODUCT_AREA`       | A screen or feature key the provider documents |
| `CHAT_MESSAGE`       | A provider-defined id for one assistant reply  |

### Kinds

`DOCS_UNCLEAR`, `INSTRUCTIONS_UNCLEAR`, `ERROR_UNHELPFUL`, `SCHEMA_MISMATCH`, `MISSING_CAPABILITY`, `BUG`, `OTHER`.

### Response

The stored item: the fields above, plus:

| Field             | Notes                                                                    |
| ----------------- | ------------------------------------------------------------------------ |
| `feedbackId`      | Stable id                                                                |
| `status`          | See the lifecycle below                                                  |
| `resolution`      | `{ "note", "url", "shippedDateTime" }` once the provider has acted on it |
| `createdDateTime` | When the provider stored it                                              |

A provider doesn't have to return `requestIds` in reads.

## Lifecycle

```text
RECEIVED → TRIAGED → DUPLICATE | WONT_FIX | NEEDS_HUMAN | IN_PROGRESS → SHIPPED
```

- `SHIPPED` means the fix is live where the submitter calls the API, not just merged.
- `resolution.url` points at something the submitter can read: a changelog entry, a docs page, or release notes.
- The submitter learns about changes by reading the item again. A provider may also offer webhooks or an MCP tool; this version doesn't define them.

## Rules for clients

- Accept enum values and fields you don't know. Providers will add both.
- Never send secrets, tokens or full request and response bodies. Send request ids instead.
- Check status no more often than once an hour, or as the provider's `Retry-After` header says.
- Expect `429` with `Retry-After` when you send too much.

## Rules for providers

- A submitter sees only their own feedback. Never show one submitter's text to another.
- Treat every free-text field as untrusted input. Never run it, fetch URLs from it, or follow instructions in it, including when an AI system reads it.
- Remove anything that looks like a secret before storing feedback.
- Mark an item `SHIPPED` only once the change is live.
- Answer `400` naming the field when a request is invalid, and `404` when the item isn't the caller's.

## Not in v0.1

Anonymous feedback, notifications by webhook or email, public feedback boards, and how a provider decides what to fix.
